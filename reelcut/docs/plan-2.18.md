# Reelcut 2.18 implementation plan

Base: version 2.17.2, commit c5c2a25. Written 2026-11-05. All `file:line` anchors refer to that commit.
Paths are relative to the repo root (`src/` = Preact UI and agent, `src-tauri/src/` = Rust backend).
Status markers used in this document:

- **CONFIRMED**: proven by code and by the PC measurements John's machine produced.
- **CODE-ONLY**: true in the code, but the visible effect has not been measured.
- **UNCERTAIN**: a hypothesis. A test is named that settles it; do not build on it until then.

Privacy rule (applies to every work package): frames, contact sheets, thumbnails or videos that show
John's children are never committed to the repo, attached to GitHub issues/PRs, or written to a synced
or shared folder. Tests use synthetic fixtures generated by ffmpeg, or real files read through
`REELCUT_FX` from a local folder outside the repo (src-tauri/src/itest.rs). Parity diagnostics on real
files report numbers only.

## 2. Root cause and parity design

### 2.1 What was compared

- John exported AI-edited drafts and compared them with the live 360 preview.
- PC facts:
  - In the 8 exported frames, the seams were aligned. There was no seam flicker.
  - Live is softer (1024 px per lens). Export is sharper, so its blend band is more visible.
  - Flow on is slightly better than flow off; flow off left a small double image.
  - Flow cost ~35%. A 12 s output took:
    - 39 s with flow and horizon on;
    - 37 s with flow on and stab off;
    - 24 s with flow and stab off.
- AI framing values in the exported drafts:
  - pitch −35..−62;
  - hfov 90..130, with corner stretch at ~121°;
  - no horizon in frame;
  - hard cuts with direction jumps;
  - one clip with yaw −180..180.
- Profile of the 24 min export:
  - 96% of the time is in the 360 prepass, at ~10 fps;
  - software decode;
  - 18 clips run one after another;
  - x264 veryfast crf 12 intermediates;
  - the final h264_qsv pass takes 59 s.

### 2.2 Confirmed causes

**C1. Geometry chosen by the AI framing (CONFIRMED; the main visible cause).**
- `headDrop` puts the head on the upper third of the frame (src/framing.ts:146-150).
- `frameSubject` aims with headroom 0.33 and has no pitch cap (src/framing.ts:173-197).
- `frameGroup`:
  - starts at hfov 90 (75 for tall frames) (src/framing.ts:277);
  - widens up to `maxHfov` 130 (105 for tall frames) (src/framing.ts:278);
  - allows pitch down to `MAX_FOLLOW_PITCH = 62` (src/framing.ts:363), applied at the clamp (src/framing.ts:338).
- The camera sits on a stick at chest or head height. Aiming at a body below the lens with the head on the upper third therefore gives pitch −35..−62. That is the "overhead CCTV" look.
- Every path is rectilinear:
  - GL preview: src/gl360.ts:126;
  - engine: src-tauri/src/pano.rs:816-829;
  - ffmpeg: src-tauri/src/media.rs:288-293.
- Rectilinear corner stretch at 16:9 is 1/cos(half-diagonal): 1.52 at 90°, 1.69 at 100°, 2.26 at 121° and 2.66 at 130°.
- The AI's default hfov is 100 in the prompt (src/agent.ts:46) and in `DEFAULT_VIEW` (src/edit.ts:274).
- The AI looks at 16:9 stills whatever the draft aspect:
  - `frames` uses 16:9 (src-tauri/src/lib.rs:754-755, src-tauri/src/media.rs:356);
  - `face_check` is 640×360 (src-tauri/src/lib.rs:589-591).
  - So on 9:16 drafts it cannot see what will be cut off.

**C2. Hard cuts with direction jumps (CONFIRMED in the drafts; CODE-ONLY as to cause).**
- Each inserted clip gets its own view (`applyOps` insert, src/agent.ts:385-392).
- SYSTEM (src/agent.ts:37-59) has no rule about keeping direction across a cut.
- Nothing in framing.ts compares the end view of clip n with the start view of clip n+1.

**C3. Live and export have stitched differently since 2.5.0 (CONFIRMED).**

| Aspect | Live preview | Export 2.17.2 | Evidence |
|---|---|---|---|
| Decode | hevc_qsv, `vpp_qsv=w=1024:h=1024`, hwdownload | software HEVC at the full 3840² per lens | src-tauri/src/live.rs:288-295; src-tauri/src/pano.rs:960-985 |
| Seam | ffmpeg v360 per lens to equirect 2048×1024, `maskedmerge` with a longitude-only linear mask | `pano::Stitcher`: flow-matched DP seam inside a band strip, flow on by default | src-tauri/src/stitch.rs:209-271, 262-265; src-tauri/src/stitch.rs:52-55, 67; src-tauri/src/pano.rs:647, 750; src/ui/Stitch360.tsx:7 |
| Band resolution | same as the picture (1024 px per lens) | strip at `out_w` px per 360°; `BAND_SHARE` 0.7. At 1920 px and hfov 90 the band has ~5.3 px/deg against ~21 px/deg for the picture | src-tauri/src/pano.rs:240, 259-264, 611-612 |
| Interpolation | linear (lanczos replaced in live) | bilinear from the full-res lens; band sampled from the strip (`bil_strip`) | src-tauri/src/live.rs:288-295; src-tauri/src/pano.rs:867-930 |
| Resampling steps | 2 (lens to equirect, then equirect to view in GL) | 1 (lens to view through the mesh) | src/gl360.ts:117-135; src-tauri/src/pano.rs:805-864 |
| Lens gains | `lutyuv` per lens | `Gain::apply`, same formula | src-tauri/src/stitch.rs:176-179, 259-260; src-tauri/src/pano.rs:300-311 |
| Rolling shutter | none | applied only outside the band | src-tauri/src/pano.rs:842-857; src-tauri/src/motion.rs:912-915 |
| Stabilisation | same quaternion track, index `round(t·fps)` | same track, `k0 = round(start·fps)` | src/ui/Viewer.tsx:171-199 (197); src-tauri/src/motion.rs:875-910, 973 |
| Projection | rectilinear | rectilinear | src/gl360.ts:126; src-tauri/src/pano.rs:816-829 |

Consequences:
- John sees one seam method and gets another.
- In the sharp export, the band comes from a strip about 4× softer than the surrounding picture. It is also not corrected for rolling shutter while its surroundings are. So it reads as a soft stripe.
- Live is uniformly soft, so the same band hides.
- The visual weight of the rolling-shutter part is CODE-ONLY (not measured).

**C4. Preview can show no stabilisation while export stabilises (CODE-ONLY).**
- `stabOf` returns `null` until `motionTrack` has a cached track.
- It starts the analysis only for files with `djmd` (src/ui/Viewer.tsx:181-191).
- Export computes the motion itself (`motion_for`, src-tauri/src/lib.rs:978).
- So for a file analysed for the first time at export, or a file without `djmd`, preview and export differ.

**C5. Export speed (CONFIRMED by the PC profile and the code).**
- Software decode with no `-hwaccel` (src-tauri/src/pano.rs:960-985).
- A new 44 MB buffer for every frame (two 3840² yuv420p lenses) (src-tauri/src/pano.rs:1046).
- `Frame::from_bytes` copies that buffer again (src-tauri/src/pano.rs:142, called at 1090).
- `par_rows` spawns OS threads on every call (src-tauri/src/pano.rs:190-199).
- Clips run one after another (src-tauri/src/lib.rs:971-1010).
- `motion_for` is called inside that loop (src-tauri/src/lib.rs:978).
- Intermediates use `libx264 veryfast crf 12` in matroska (src-tauri/src/motion.rs:981).
- The progress weight of the prepass is fixed at 60 (src-tauri/src/lib.rs:894).
- Flow, on by default, costs ~35%.

**C6. Silent fallbacks (CONFIRMED).**
- When the engine fails, export falls back to the ffmpeg stitch. It only writes `eprintln!` (src-tauri/src/lib.rs:899, 907).
- The release build has no console (src-tauri/src/main.rs:2), so nobody ever sees that.
- A failed motion analysis returns `Ok(None)` (src-tauri/src/motion.rs:936-960). The export then goes out unstabilised without a word.
- ff.rs keeps only 3 stderr lines (src-tauri/src/ff.rs:198-201).

**C7. AI exports skip loudness normalisation (CONFIRMED).**
- `export_draft` builds its options without `loudnorm` (src/agent.ts:1070-1080).
- `toPlan` reads `!!o.loudnorm` (src/edit.ts:855).
- The dialog defaults to `loudnorm: true` (src/exporter.ts:34) and does not remember the last choice (src/ui/ExportDialog.tsx:16).

**C8. Deletion is permanent and saving is not crash-safe (CONFIRMED).**
- `store_delete` calls `remove_file` (src-tauri/src/lib.rs:176-183).
- `deleteProject` (src/store.ts:184-187) is called from a one-step confirm (src/ui/Home.tsx:103-109).
- The "remove empty projects" button counts only assets and clips, not chats (src/ui/Home.tsx:62, 73).
- `store_set` writes tmp then renames, without fsync (src-tauri/src/lib.rs:167-174).
- `loadProjects` silently skips unreadable files (src/store.ts:144-152).
- The undo stack exists only in memory (src/store.ts:219-290).
- Deleting a chat warns "되돌릴 수 없습니다" and removes it (src/ui/AgentPanel.tsx:267-274).
- The Claude Code transcripts live under `data/claude/config`:
  - `CLAUDE_CONFIG_DIR` is set at src-tauri/src/cc.rs:351-358;
  - the path comes from `config_dir` at src-tauri/src/cc.rs:247-249;
  - no `cleanupPeriodDays` is set, so Claude Code's default retention applies.
- John deleted 4 projects himself from Home; 55 transcripts survive on disk.

### 2.3 Refuted

- **Seam flicker or seams that jump from frame to frame.** Refuted: no flicker in John's 8 frames.
- **Flow makes the seam worse.** Refuted: flow on is slightly better. Flow off leaves a small double image, and that same double image is present in live, where the softness hides it.
- **Export levels or stabilises differently in maths.** Refuted:
  - both paths draw `r = stab·(q_view·d)` from the same quaternion track (src/gl360.ts:61-64; src-tauri/src/motion.rs:875-895, 899-910);
  - the defaults are the same (horizon, strength 1, rs true; src-tauri/src/motion.rs:23-55);
  - only the exceptions in C4 and U1/U2 remain.
- **The final encode makes export slow.** Refuted: the final h264_qsv pass is 59 s out of 24 min.
- **Flow alone explains the slowness.** Refuted: flow costs ~35%, while the prepass is ~23 of 24 minutes.

### 2.5 Parity design: one seam method

**P1. Seam model.**
- Add `seam: "linear" | "flow"` to `Stitch`:
  - TS: `seam?: "linear" | "flow"` next to `flow?` (src/types.ts:15-21);
  - Rust: `#[serde(default)] seam: String` in the Rust `Stitch`.
- Default `"linear"`. The legacy `flow: true` is ignored on load. It was the default (src/ui/Stitch360.tsx:7), so it does not record a user choice.
- The Stitch360 flow checkbox (src/ui/Stitch360.tsx:40-46) becomes a select:
  - "이음새: 미리보기와 같게 (기본)";
  - "정밀 (느림, 미리보기에는 안 보임)".
- Shared weight, used by both paths:
  ```
  σ  = asin(cos(lat) · cos(lon))          // angle from the front-lens boundary, in the front-lens frame
  b  = blend_width(fov)                    // src-tauri/src/stitch.rs:86-88, degrees
  wF = clip((σ + b/2) / b, 0, 1)           // weight of the front lens; back = 1 − wF
  ```
  On the equator, σ = 90 − |lon|. So wF equals today's live mask `clip((90 + b/2 − |lon|)/b)` (src-tauri/src/stitch.rs:262).
- Live (stitch.rs `graph`):
  - replace the longitude-only mask (src-tauri/src/stitch.rs:262-265) with a 2-D mask;
  - it is rendered once per graph at 1024×512 and scaled bilinear:
  ```
  geq=lum='255*clip((asin(cos((0.5-(Y+0.5)/H)*PI)*cos(((X+0.5)/W*2-1)*PI))*180/PI + B/2)/B,0,1)'
  ```
  `B` is formatted as a number, the same way as today's `{b:.4}`.
  - Must verify: the front-lens axis sits at (lon 0, lat 0) of the graph's equirect. WP2 has a unit test on the graph string.
  - If the alignment rotation is applied to the front lens instead, the mask goes through the same `v360` rotation.
- Engine: `enum Seam { Linear, Flow }` replaces `flow: bool` in `Stitcher::new` (src-tauri/src/pano.rs:607).
  - In `Linear`, `frame()` (src-tauri/src/pano.rs:867-930) skips the strip, `update_seam` and `blend_band` (pano.rs:619, 647, 750). For every output pixel it uses:
  ```
  s   = mesh[5]                       // already asin(dc[2]) in the front-lens frame, pano.rs:856
  wF  = clamp((s + b/2) / b, 0, 1)    // b in radians
  out = wF·gF.apply(bil(front)) + (1 − wF)·gB.apply(bil(back))
  ```
  - The mesh layout is unchanged; slot 5 already holds σ.
  - Only one lens is sampled when wF is 0 or 1.
  - Rolling shutter is applied to both samples inside the band, or to none (see P3).
- `Flow` keeps today's code. It is labelled as not previewable, and it is the only intentional difference left.
- Sharpness: export samples the full-res lens with one bilinear step, so it stays sharper than live by design. Seam position and width are now identical.
  - WP13 adds an optional sharper live preview (`vpp_qsv` 1536/2048).

**P2. One projection.**
- One function maps (u, v, hfov, dist, aspect) to a view direction (§4.4). It is used by:
  - the GL shader (src/gl360.ts:117-135);
  - the engine mesh (src-tauri/src/pano.rs:816-829);
  - the ffmpeg fallback (src-tauri/src/media.rs:288-293).
- A fixture test keeps the copies equal (WP5).

**P3. Stabilisation and levelling consistency.**
- Rolling shutter is gated:
  - `const RS_VERIFIED: bool = false;` in motion.rs. While false, `rs_of` returns `None` (src-tauri/src/motion.rs:912-915).
  - The Stab360 RS checkbox is disabled with the tooltip "검증 중 (2.18에서는 꺼짐)".
  - WP4 flips the flag only after U1 passes. This also removes the in-band/out-of-band discontinuity.
- Frame-index rule (both paths):
  ```
  k(t_src) = round(t_src · fps_src)
  ```
  - `t_src` is the presentation time of the decoded source frame.
  - Export: `k = k0 + n·every` (`every` = 1 unless decimating, §2.6), with `k0 = round(start·fps_src)` as today (motion.rs:973, 1006, 1032, 1053).
  - Preview: `requestVideoFrameCallback` `mediaTime` replaces `video.currentTime` during playback for the index at Viewer.tsx:197 and the draw at Viewer.tsx:483.
- Motion availability:
  - the preview starts `analyzeMotion` for every 360 asset whose stab mode is not `off`, not only `djmd` (src/ui/Viewer.tsx:188-191);
  - the viewer hint (src/ui/Viewer.tsx:756) shows "흔들림 정보 분석 중" or "흔들림 정보 없음 (내보내기도 보정 없음)".
- Per-clip stabilisation: `Clip.stab` overrides `Asset.lens.stab`, needed for the toolbar scope (§4).
  - The resolution order (`clip.stab ?? asset.lens.stab ?? DEFAULT`) is implemented once in TS (`stabFor`, src/edit.ts) and carried in the plan Seg (src/edit.ts:785).

**P4. No silent fallbacks.**
- `export` returns `warnings: string[]` in its done event (src-tauri/src/lib.rs:105-107 `emit`).
- Warnings are written to the export log and shown by `exporter.ts` / ExportDialog after the export.
- Sources:
  - engine failure, now per clip: only the failing clip falls back to `stitch::graph`;
  - `motion_for` returning `None` ("흔들림 정보 없음: 보정 없이 내보냄");
  - QSV failure falling back to software decode;
  - a lossy intermediate chosen because of low disk space.

**P5. Parity tests (gates).**

| Test | Where | Gate |
|---|---|---|
| `front_weight` equals the old 1-D mask on the equator, w(σ)+w(−σ)=1, monotone | Rust unit (stitch.rs) | exact to 1e-9 |
| The live geq mask rendered by ffmpeg equals `front_weight` per pixel | Rust itest, synthetic, cloud | max abs diff ≤ 1/255 + 1 LSB |
| Engine `Linear` equirect (`FrameSetup.hfov = None`) vs `stitch::graph` Out::Equi with linear interp, same synthetic fixture (stitch.rs:722-770, `psnr` at stitch.rs:738) | Rust itest, cloud | Y PSNR ≥ 40 dB full frame, ≥ 36 dB inside ±b |
| GL `viewDir` (TS port) vs Rust `proj::view_dir` on a JSON grid (pattern of tests/fixtures/framing.json, src-tauri/src/framing.rs:163-180) | vitest + cargo test | ≤ 1e-6 rad |
| `diag_parity` on John's file: live-path frame vs engine frame at 3 times × 2 views | PC, numbers only | seam centre offset ≤ 0.5 px at 1024 scale; band PSNR ≥ 35 dB after downscaling the export to live resolution |

If a measured baseline misses a gate, fix the cause, not the gate. The one exception is the documented sharpness difference, which the downscale step removes.

### 4.4 Projection maths (general perspective, dist d in 0..1)

- d = 0 is rectilinear; d = 1 is stereographic. The radius of a ray at angle `a` from the view axis:
```
r(a, d)  = (1 + d)·sin a / (d + cos a)
inverse: k = ρ/(1 + d);  a(ρ, d) = atan k + asin(k·d / √(1 + k²))
r_e      = r(hfov/2, d)                      // half-width in projection units
p        = (u·r_e, v·r_e·H/W),  u,v ∈ [−1, 1]
ρ = |p|; a = a(ρ, d); dir = (p/ρ · sin a, cos a)       // view space, z forward
shape stretch(a) = (1 + d·cos a)/(d + cos a)            // = 1/cos a for d = 0
vfov     = 2·a(r_e·H/W, d);  dfov = 2·a(r_e·√(1 + (H/W)²), d)
fovMax(d) = min(330, 2·acos(−d) − 20)                   // replaces the fixed 20..160 clamp
```
- **왜곡 보정** rule. `D` = rectilinear diagonal FOV of the current view.
  - Set `d = clamp((D − 90)/60, 0, 1)` and keep the short side's FOV, solving for the new hfov via `r_e = r(short/2, d)·W/H`.
  - 16:9: 100° becomes 105.1° (d 0.29, ×1.69 → ×1.39); 121° becomes 137.1° (d 0.63, vfov 89.7 kept, ×2.26 → ×1.31).
  - For 9:16 and 1:1 the short side is horizontal, so hfov stays and only `d` changes.
- **GLSL** (src/gl360.ts; uniforms set where `tx` is computed today, src/gl360.ts:24, 126). The rest of the shader (`r = stab·(q_view·d)`, src/gl360.ts:61-64) is unchanged:
  ```glsl
  uniform float u_dist, u_re, u_aspect;          // u_re = r(hfov/2, d) computed on the CPU
  vec3 viewDir(vec2 uv) {                        // uv in [-1, 1]^2
    vec2 p = vec2(uv.x, uv.y * u_aspect) * u_re;
    float rho = length(p);
    if (rho < 1e-6) return vec3(0.0, 0.0, 1.0);
    float k = rho / (1.0 + u_dist);
    float a = atan(k) + asin(clamp(k * u_dist / sqrt(1.0 + k * k), -1.0, 1.0));
    return vec3(p / rho * sin(a), cos(a));
  }
  ```

  - `motion::setup_fn` (src-tauri/src/motion.rs:875-895) passes it on, and `render::view_anim` (src-tauri/src/render.rs:434) interpolates it.
- **ffmpeg v360 fallback** (`v360_flat`, src-tauri/src/media.rs:288-293):
  - `d < 0.5`: `output=flat` with the same h_fov (approximation; logged as a warning);
